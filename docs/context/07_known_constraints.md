# 已知约束与风险边界

当前 HNBLUE V1.0 启动成本较高，涉及 Vue 前端、Spring Boot 后端、Flask 模型服务、MySQL、Redis、AnythingLLM 桌面端和 DeepSeek API。V2.0 开发需要优先降低启动复杂度，建议提供 Docker Compose、统一环境变量、示例配置文件和一键启动说明。若短期无法全部容器化，至少需要明确每个服务的启动顺序、端口、依赖和健康检查方式。

完整 WebGIS 功能暂不作为 V2.0 的硬性目标。上位实施方案中提到 WebGIS、ArcGIS 空间分析和碳储量时空格局可视化。当前开发阶段可以先使用 ECharts 地图、普通文件元数据列表、静态图件和可下载数据包实现演示。后续再接入 Leaflet、Mapbox、Cesium、GeoServer 或其他 GIS 服务。

真实通量塔连续数据、无人机影像和遥感产品可能尚未稳定交付。系统设计应支持“待接入状态”。页面中应使用数据来源字段标注真实数据、公开数据、模拟数据和待接入数据。任何演示数据都不应被写成正式监测结论。

CatBoost 模型可以作为 V1.0 的重要能力保留，但需要注意适用边界。当前模型主要基于 BAAD 或类红树林样本构建，尚需更多海南本地样方和无人机结构变量进行区域校准。系统展示时可以强调模型推理、解释和辅助评估功能，避免将其表述为已经完成省域精确核算。

AI 碳助手应作为解释和材料辅助工具。其回答需要受私域知识库、数据口径和不确定性说明约束。涉及政策、数据结论、项目验收和科学判断时，应优先引用系统内已有数据与文档。

数据库存在多个 Schema 或分散脚本时，应先进行清点和归并。建议在 `db/` 下建立 `schema.sql`、`seed_wenchang_demo.sql`、`migration_notes.md` 和 `data_dictionary.md`。若存在无法合并的旧表，应保留兼容层或迁移说明，避免破坏现有页面接口。
