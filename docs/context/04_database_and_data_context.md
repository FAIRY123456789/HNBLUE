# 数据库与数据治理上下文

HNBLUE 的数据库设计以“海南蓝碳系统生态碳汇数据库”为核心。该数据库位于平台表达层与资料收集层之间，上方承接 WebGIS/可视化分析、AI 碳助手、模型解释和阶段性汇报材料，下方承接地面调查、高分辨率卫星遥感、无人机遥感、公开大数据、碳通量监测和文献资料。当前数据库已经从单一 `hnblue` 库扩展为多个 `hainan_blue_carbon_*` Schema，说明项目已经进入 V2.0 数据治理设计阶段。

HNBLUE 1.0 当前只与 `hnblue` 库联动。该库保留用户系统和模拟可视化页面所需的展示型指标表，包括区域年度碳储量、通量组成、通量影响因子、多碳指标、物种组成、区域简介、年度趋势、区域分区、经济价值估算和通用指标展示数据。该库短期内应冻结为 V1.0 演示层，不直接删除模拟数据，不强行修改字段名。已有页面继续通过旧接口读取 `hnblue`。V2.0 数据库建设应在新的规范层中推进，再通过后端适配层或 SQL 视图向旧页面输出同等结构的数据。

V2.0 数据库的核心目标是把展示型指标表升级为数据治理型结构。所有数据都应明确来源、版本、空间范围、时间范围、处理方法、质量标识、共享范围和关联文件路径。真实数据、公开数据、文献数据、模型输出和模拟数据需要在来源表和资产表中分开标识。模拟数据统一使用 `source_category = 'SIMULATED'` 和 `is_simulated = 1`，避免在演示、论文、汇报和后续真实数据接入时发生混淆。

V2.0 建议保留多 Schema 组织方式，并明确各 Schema 边界。`hainan_blue_carbon_core` 作为主数据和资产索引中心，保存区域、项目、站点、数据来源、数据版本、指标字典、质量标识和数据资产索引。`hainan_blue_carbon_ground` 保存地面调查批次、样方、样木、土壤样品、样方物种组成和样方碳库汇总。`hainan_blue_carbon_flux` 保存通量塔站点扩展信息、原始文件索引、30 分钟观测、日尺度聚合和质量事件。`hainan_blue_carbon_satellite` 保存卫星遥感产品元数据、区域统计指标、红树林覆盖结果和网格尺度碳储/冠层高度结果。`hainan_blue_carbon_uav` 保存无人机航飞任务、无人机产品、样区统计、物种识别和碳储量反演结果。`hainan_blue_carbon_model` 保存 CatBoost、SHAP、敏感性分析、模型运行、预测结果和解释图件。`hainan_blue_carbon_intl` 保存 BAAD、Tallo、异速生长方程、公开遥感产品、文献碳储量记录和其他外部参照数据。`hainan_blue_carbon_local` 保存文昌示范区和海南本地展示聚合结果，并提供旧页面适配视图。

冷热存储规则应保持稳定。热数据进入 MySQL，包括区域、站点、样地、样木测量、土壤样品、通量 30 分钟统计、通量日尺度统计、遥感元数据、遥感区域统计、无人机任务元数据、无人机区域指标、模型运行记录、模型预测结果、指标字典、来源登记、版本记录和质量标识。冷数据进入文件目录、NAS、对象存储或 URL，包括 GeoTIFF、无人机正射影像、DSM、DEM、CHM、点云、原始通量文件、10Hz 高频数据、原始 CSV/Excel、航飞照片、模型文件、SHAP 图件、响应曲线图、PDF 报告和压缩包。MySQL 中只保存冷数据的文件名、相对路径、格式、大小、哈希、空间范围、时间范围、来源、版本和状态。

后续通过浏览器检索数据时，应按统一入库顺序推进。第一步在 `core.t_data_source` 中记录数据名称、发布机构、网页地址、访问日期、下载日期、许可证、引用格式和是否模拟数据。第二步在 `core.t_data_version` 中记录版本编码、发布时间、入库时间、处理级别和处理方法。第三步如存在文件，则在 `core.t_data_asset_index` 中登记文件路径、格式、大小、哈希、空间范围、时间范围和共享范围。第四步将清洗后的结构化结果写入对应业务 Schema。第五步把适合前端展示和汇报的区域年度指标写入 `local.t_local_region_yearly_metric` 或 `local.t_local_visualization_metric`。

文昌示范区在 V2.0 中应作为首个可运行示范数据包。它的作用是固化区域对象、站点对象、数据来源、指标口径、质量标识、模型输出和展示聚合方式。文昌最小数据包可以先包含区域档案、示范数据说明、年度碳储量与通量指标、优势物种指标、遥感产品元数据、无人机任务元数据和模型预测结果。待真实通量、样方和遥感产品交付后，再用真实数据替换模拟数据或公开数据，同时保留旧版本记录。

V2.0 表结构文件为 `hnblue_v2_schema.sql`。该 SQL 文件适合在新的开发数据库或测试实例中运行。它包含 `DROP TABLE IF EXISTS`，因此不建议直接在已有演示库中执行。执行前应备份当前所有 Schema。当前阶段的安全策略是保留 `hnblue` 旧库，另行建立 V2.0 规范层。旧页面继续运行，V2.0 数据采集、浏览器检索、公开数据整理、文献数据整理和真实数据接入都进入 `hainan_blue_carbon_*` 规范库。

配套的详细设计文件为 `docs/context/database_v2_design.md`。该文件解释了各 Schema 的职责、冷热存储规则、数据填充顺序、旧页面适配方式和执行注意事项。建议将本文件作为新的 `docs/context/04_database_and_data_context.md`，替换旧版 04；同时保留 `database_v2_design.md`，作为数据库实施和后续 Codex 重构的专门依据。
