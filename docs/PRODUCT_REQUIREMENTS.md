# HNBLUE 产品需求与设计决策

## 1. 产品定位

HNBLUE 是蓝碳数据治理与证据辅助分析原型。它的核心价值不是替用户给出“唯一正确结论”，而是把来源、口径、区域、时间、单位、质量状态、模型边界和处理流程组织成可追溯的工作界面。

## 2. 目标用户与任务

| 用户 | 主要任务 | 产品必须避免 |
|---|---|---|
| 数据管理人员 | 查看数据目录、质量标记、来源和变更工作单 | 把未知来源记录伪装成正式数据 |
| 研究人员 | 浏览文献、结构变量、模型输出和解释图 | 把相关性解释成因果或外推精度 |
| 业务研判人员 | 快速理解区域材料和证据缺口 | 把模型答案当作法定结论 |
| 演示与评审人员 | 理解系统架构、Agent 设计和工程边界 | 暴露内部数据、凭据和部署细节 |

## 3. 核心需求

### P0：可信边界

- 每条记录保留来源、单位、时间、空间、处理状态和模拟/代理标记。
- 浏览器不能直接访问数据库、模型服务、RAG 服务或生成供应商。
- 私有知识、真实数据、对话和密钥不得进入公开仓库。
- AI 无充分证据时必须拒答，不能用模型常识补齐数值或政策结论。

### P0：任务可完成

- 用户可以按区域、年份、指标和来源浏览结构化数据。
- 用户可以查看数据来源和质量信息，而不是只有单一数值。
- 模型输入、输出和解释必须明确标注为模型能力。
- Agent 回答应展示引用、证据状态和降级状态。

### P1：治理闭环

- 数据变更通过工作单提出、受理、审核、批准/驳回并保留动作记录。
- 不同角色只能看到和执行其权限范围内的动作。
- 热点查询可缓存，但缓存键、TTL 和失效逻辑必须可解释。

### P1：公开可复现

- 开发者可使用合成数据启动主要页面和解析器。
- 开发者可用合成知识构建索引、运行检索和执行测试。
- README、架构、API、数据策略和限制必须与代码保持一致。

## 4. 关键产品决策

1. **证据优先于回答流畅度。** 宁可明确“证据不足”，也不提供无法追溯的完整答案。
2. **公开快照不等于生产事实。** 静态 JSON、GeoJSON 和图件用于可复现演示，必须与实时数据库状态区分。
3. **Agent 是受约束编排器。** 生成模型只是一个可替换步骤；检索、政策、安全、记忆和回退由应用掌握。
4. **不可用也是产品状态。** 缺少数据、模型或生成服务时显示边界与下一步，不伪造成功。
5. **治理变更显式化。** 重要数据修改进入工作单状态机，而不是在前端提供任意写数据库入口。

## 5. 非目标

- 不替代官方监测、MRV、核证、碳交易登记或法律意见；
- 不在公开仓库复现真实知识库、生产数据库或内部部署；
- 不将历史实验指标包装为当前生产承诺；
- 不承诺生成模型始终在线，也不让其不可用阻断核心数据功能。

## 6. 成功标准

- 代码仓库不包含真实凭据、私有知识、生产对话或原始数据；
- 关键记录和 Agent 回答具有可见来源与证据状态；
- 合成样例可覆盖主要解析、检索、拒答和引用校验流程；
- 数据、模型、Agent 三类能力在界面和文档中具有清晰边界；
- 新开发者能从双语 README 找到架构、配置、数据策略和核心代码入口。
